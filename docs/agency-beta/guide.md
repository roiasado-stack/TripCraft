# מדריך הבטא לסוכני נסיעות

המדריך הזה מסביר איך עובדת "סביבת הסוכן" ב-TripCraft: איפה היא יושבת, איפה הנתונים, מי רואה מה, איך
מאשרים סוכן ומה עושים כשמשהו נתקע. כל משפט כאן נבדק מול הקוד (מסכים, migrations 022–023 ופונקציות
ה-Edge `ask` ו-`generate`). מילים טכניות מוסברות במילון בסוף.

---

## 1. מה זה ולמה

סוכן נסיעות כבר מקבל את כל המסמכים: כרטיסי טיסה, אישור מלון, השכרת רכב. בבטא, **המסמכים בונים את
הטיול**, והסוכן רק בודק ושולח ללקוח. היעד: פחות מ-3 דקות מהמסמכים עד קישור שנשלח בוואטסאפ.

שלושה מסכים:

1. **טיול חדש מהמסמכים** (`/agent/new`) — מעלים עד 8 קבצים. ה-AI מזהה יעד, תאריכים, נוסעים, טיסות, מלונות
   ורכב. הסוכן מאשר את מה שזוהה.
2. **בדיקה אחרונה** — שם הלקוח, הטלפון שלו, שם הטיול, יעד, תאריכים ונוסעים. לחיצה על "יצירת הטיול".
3. **שליחה ללקוח** (`/agent/send/...`) — הודעה מוכנה עם קישור לדף הטיול וקישור הצטרפות. "שליחה בוואטסאפ"
   או "העתקת ההודעה".

מתחת לכפתור "טיול חדש מהמסמכים" יש את **הטיולים שלי**: רשימה אחת עם סטטוס לכל טיול (טיוטה / נשלח / יוצא
בקרוב / בחו"ל / חזר / חסר משהו), חיפוש לפי לקוח או יעד, וסינון **"דורשים טיפול"**.

## 2. איפה זה יושב

זו **לא מערכת נפרדת**. זו אותה אפליקציה, באותה כתובת (tripcraft-lac.vercel.app), עם מסלולים חדשים שנפתחים
רק לסוכן מאושר.

```
 הטלפון של הסוכן / של הלקוח
          │
          ▼
 ┌──────────────────────┐   הקוד עצמו ב-GitHub. כל merge לענף הראשי → Vercel בונה ומפרסם
 │ Vercel               │   את האתר: tripcraft-lac.vercel.app
 │ האתר (React)         │   /agent  /agent/new  /agent/send/:id   ← סוכן מאושר
 │                      │   /admin/agents                         ← רק אתה (admin)
 │                      │   /share/:slug                          ← הלקוח, בלי התחברות
 └─────────┬────────────┘
           │ כל קריאה נושאת את זהות המשתמש המחובר
           ▼
 ┌──────────────────────┐
 │ Supabase             │   מסד נתונים (Postgres) + כללי RLS — כאן נאכף "מי רואה מה"
 │                      │   אחסון קבצים: trip-docs (פרטי), agency-logos (ציבורי)
 │                      │   Edge Functions: generate (סריקת מסמכים, AI), ask (הסוכן החכם, כשרות ושבת)
 └─────────┬────────────┘
           ▼
   Anthropic (Claude) — קורא את המסמכים | Google, OpenStreetMap, Hebcal, Wikipedia — מקומות, זמנים ותמונות
```

| חלק | איפה | מי נוגע בו |
|---|---|---|
| קוד | GitHub | אתה ו-Claude, דרך PR |
| האתר | Vercel | נבנה מחדש אחרי merge |
| נתונים, קבצים, הרשאות | Supabase | migrations שאתה מדביק ב-SQL Editor |
| AI | Anthropic, דרך Edge Functions | המפתח שמור כסוד ב-Supabase, אף פעם לא בדפדפן |

## 3. איפה הנתונים

הכל באותו Supabase של האפליקציה. אין מסד נפרד לסוכנים.

| טבלה / מקום | מה יש בה | מי רואה |
|---|---|---|
| `agent_accounts` | שורה לכל סוכן: סטטוס (ממתין / פעיל / מושעה), שם סוכנות, טלפון, 4 המכסות, מתי ביקש ומתי הוחלט | הסוכן רואה רק את השורה שלו. אתה (admin) רואה את כולן. **אף אחד לא כותב בה ישירות** — רק דרך פונקציות מוגנות (בקשה, אישור, השעיה, שינוי מכסה) |
| `user_roles` | התפקיד `agent` נוסף כאן באישור ונמחק בהשעיה | — |
| `trip_clients` | שם הלקוח והטלפון שלו, לכל טיול | **רק בעל הטיול** (הסוכן). לא חברי הטיול, לא הדף הציבורי |
| `trips`, `participants`, `flights`, `stays`, `transfers`, `itinerary_items`, `documents`, `trip_updates` | הטיול עצמו — אותן טבלאות כמו של כל משתמש | הסוכן, ומי שהוא צירף לטיול לפי התפקיד שלו |
| `profiles` | צבע המותג וכתובת הלוגו (מהגדרות). שם הסוכנות שבדף הציבורי **לא** מכאן — הוא השם שאושר ב-`agent_accounts` | — |
| `agent_runs` | כל קריאת AI ועלותה, וכל קריאה ל-Google | משמש למכסות ולמסך האדמין |
| bucket `trip-docs` (**פרטי**) | המסמכים שהסוכן העלה כדי לבנות טיול, בתיקייה של הסוכן | נפתח רק בקישור זמני למי שמורשה |
| bucket `agency-logos` (**ציבורי**) | לוגו הסוכנות. PNG / JPEG / WebP עד 1MB, בלי SVG | כל מי שיש לו את כתובת הקובץ. אי אפשר לקבל רשימה של כל הלוגואים |

**RLS = כל סוכן רואה רק את הטיולים שלו.** זה לא רק "המסך לא מראה". מסד הנתונים עצמו מחזיר לכל משתמש רק את
השורות שמותר לו. גם אם מישהו יעקוף את המסך וישלח בקשה ישירה, הוא יקבל רשימה ריקה. יש לזה בדיקות אוטומטיות
(סעיף "בדיקות אוטומטיות" ב-test-checklist.md).

## 4. איך סוכן נכנס

- **אימייל וסיסמה, או "המשך עם Google".** כל חשבון Google עובד, כולל Google Workspace של הסוכנות
  (למשל noa@agency.co.il).
- **אין "כניסה בשם הסוכנות".** כל סוכן הוא אדם עם חשבון משלו. שם, צבע ולוגו של הסוכנות הם רק המיתוג שהלקוח
  רואה בדף הטיול.
- **מגבלת בטא:** 3 סוכנים מאותה סוכנות = 3 חשבונות נפרדים, ו**הם לא רואים זה את הטיולים של זה**. סוכנות עם
  טיולים משותפים לכמה סוכנים היא שלב 2, כי טעות שם = סוכן רואה לקוחות של מתחרה.

## 5. איך סוכן מקבל גישה

1. הסוכן נרשם כרגיל ונכנס.
2. **הגדרות → "אני סוכן/ת נסיעות"** → שם הסוכנות (חובה) וטלפון → "שליחת בקשה".
   בהגדרות מופיע עכשיו "הבקשה בבדיקה". אפשר לערוך את הפרטים כל עוד הבקשה ממתינה.
   (משתמש דמו — "נסו בעצמכם" בלי חשבון — לא יכול לבקש.)
3. **אתה** נכנס ל-**הגדרות → סוכנים** (`/admin/agents`). הבקשה מופיעה ב"בקשות ממתינות" עם המייל, הטלפון
   ותאריך הבקשה. "אישור" או "דחייה".
4. אחרי אישור, **הסוכן צריך לרענן** את האפליקציה (או ללחוץ בהגדרות על "הגישה אושרה — לפתיחת סביבת הסוכן").
   התפקיד נטען בכניסה, ולכן בלי רענון הוא עדיין לא רואה את `/agent`.
5. מעכשיו יש לו ברשימת הטיולים שורה "סביבת הסוכן", ובהגדרות "מיתוג סוכנות": צבע, לוגו, ושם הסוכנות **לקריאה
   בלבד**.

**שם הסוכנות בדף הלקוח = השם שאישרת** (מהבקשה). הסוכן לא יכול לשנות אותו בעצמו, כדי שאף אחד לא יקרא לעצמו
אחרי שאושר בשם של סוכנות אחרת. בהגדרות כתוב לו "לשינוי השם פנו אלינו". **איך משנים:** הסוכן פונה אליך. בבטא אין
לזה מסך, אז ב-SQL Editor של Supabase:
```
UPDATE public.agent_accounts SET agency_name = 'השם החדש'
WHERE user_id = (SELECT id FROM auth.users WHERE email = 'המייל של הסוכן');
```

## 6. איך מנהלים — מסך "סוכנים"

רק לך (תפקיד admin). שלושה חלקים:

- **בקשות ממתינות** — אישור / דחייה.
- **סוכנים פעילים** — לכל סוכן 5 פסי שימוש: AI היום, AI החודש, חיפושי Google היום, תמונות Google היום,
  טיולים פעילים. פס כחול = תקין, צהוב = מעל 80%, אדום = המכסה נוצלה. כפתורים: **"מכסות"** ו**"השעיה"**.
- **מושעים** — כפתור "אישור מחדש".

**מה השעיה עושה:**
- התפקיד `agent` נמחק. אחרי רענון, `/agent` מחזיר אותו לדף הבית, ובהגדרות כתוב "גישת הסוכן מושעית".
- רשימת "הטיולים שלי" בסביבת הסוכן מתרוקנת מיד (מסד הנתונים כבר לא מחזיר אותה), גם לפני רענון.
- קריאות AI חוזרות למכסה של משתמש רגיל ($2 ליום).
- הלוגו, השם והצבע **נעלמים מהדפים הציבוריים** שלו (מוצגים רק לסוכן פעיל).
- **הטיולים נשארים** אצלו כטיולים רגילים, והקישורים שכבר נשלחו ללקוחות ממשיכים לעבוד.
- "אישור מחדש" מחזיר הכל, כולל המכסות הקודמות.

**דחייה** של בקשה עובדת אותו דבר כמו השעיה (במסד הנתונים שתיהן "מושעה"), ולכן בקשה שנדחתה מופיעה ב"מושעים".

**שינוי מכסה** נאכף בקריאת ה-AI הבאה של הסוכן, בלי רענון.

| טיולים פעילים | 30 | 500 | טיול "פעיל" = שעוד לא הסתיים (או בלי תאריך סיום). טיול שחזר לא נספר |

**נשאר בתוקף לכולם:** תקרת האפליקציה כולה, **$15 ליום** לכל המשתמשים יחד, ו-600 חיפושי כשרות ב-Google
בחודש לכל האפליקציה. **חולשה:** ביום קיצוני סוכנים ומשתמשים רגילים חולקים את התקרה הזו.

**"היום" מתאפס בחצות UTC**, כלומר ב-03:00 בבוקר שעון ישראל בקיץ (02:00 בחורף).

**מה הסוכן רואה כשמגיע למגבלה:**
- **AI ליום:** "מכסת ה-AI להיום נוצלה. אפשר לנסות שוב מחר — כל שאר הטיול עובד כרגיל."
- **AI לחודש:** "מכסת ה-AI החודשית של החשבון נוצלה. פנו אלינו להגדלה — כל שאר הטיול עובד כרגיל."
  (אם סוכן פונה — "מכסות" במסך הסוכנים והגדלה של "AI לחודש".)
- **Google:** אין הודעת שגיאה. פשוט פחות תוצאות כשרות או בלי תמונה למקום.
- **טיולים פעילים** (ביצירת טיול מהמסמכים): "הגעת למכסת הטיולים הפעילים בחשבון. אפשר למחוק טיול ישן או
  לפנות אלינו."

## 8. מה הלקוח רואה

**דף הטיול הציבורי** (`/share/...`) נפתח **בלי התחברות**, לכל מי שיש לו את הקישור:
- למעלה: פס בצבע הסוכנות, הלוגו והשם, "הטיול שלכם מאת…". (הצבע מופיע רק כפס. הוא לא צובע את התמונה הראשית
  ולא את הטקסט, כדי שהדף יישאר קריא בכל צבע שסוכן בוחר.) השם הוא השם שאישרת. הלוגו מופיע רק אם הסוכן העלה
  אחד בהגדרות → מיתוג סוכנות — סקריפט הדמו לא מעלה לוגו, אז **לפני הדגמה העלו לוגו בחשבון הדמו**.
- שם הטיול, יעד, תאריכים, תמונה של היעד (מוויקיפדיה) אם יש.
- שם וטלפון של המדריך (אם הוזן), עדכונים, קישור לאלבום תמונות.
- טיסות (מסלול, שעה, חברה ומספר טיסה), מלונות (שם, כתובת, תאריכים, מפה), מסלול יומי, מומלצים.
- בתחתית: "נבנה עם TripCraft" כטקסט שקט, בלי כפתור.

**מה לא מופיע בדף הציבורי:** מספרי הזמנה, רשימת הנוסעים, מסמכים ודרכונים, הערות, צ'קליסט, **ושם הלקוח
והטלפון שלו**.

**הקישור האישי ללקוח** (בהודעת הוואטסאפ, מ-18.10, migration 024) נותן חשבון מלא בטיול, ולכן:
- הוא **עובד פעם אחת**. מי שנכנס בו הופך ל**לקוח הראשי**, והקישור נסגר.
- **עם מייל של הלקוח** (שדה "מייל" במסך השליחה): נפתח רק לחשבון עם המייל הזה, אחרי שאושר. הלקוח נכנס מיד, בלי
  אישור של הסוכן. חשבון אחר רואה "הקישור הזה מיועד ל-da***@gmail.com", והקישור לא נצרך.
- **בלי מייל:** מי שנכנס מחכה ל**אישור אחד** של הסוכן. אפשר לאשר במסך "שליחה ללקוח" עצמו, או בכפתור השיתוף →
  "ממתינים לאישור".
- **הלקוח הראשי מנהל את המשפחה בעצמו:** בכפתור השיתוף בתוך הטיול יש לו קישור לקבוצה שנכנס מיד, העתקה ושליחה
  בוואטסאפ, "החלפת הקישור" אם הגיע למי שלא צריך, ורשימת מצטרפים עם הסרה. הסוכן לא מאשר אף אחד מהמשפחה.
- ללקוח הראשי ולמשפחה יש הרשאת **משתתף**: הם רואים הכול, מוסיפים המלצות, מסמנים בצ'קליסט ומפרסמים עדכונים.
  הם **לא** משנים טיסות, מלונות או מסלול, ולא יכולים להוציא את הסוכן או עורך.
- הסוכן רואה ליד הלקוח תג "לקוח ראשי", ויכול להעביר את התג למישהו אחר ("סימון כלקוח ראשי"), או לבטל קישור
  אישי שנשלח ולשלוח חדש.
- גם אחרי שהצטרפו, **אף אחד לא רואה את שם הלקוח, הטלפון והמייל** — אלה של הסוכן בלבד.
- **חשוב בייצור:** הנעילה למייל סומכת על כך שהמייל אומת. ב-Supabase → Authentication → Sign In / Providers →
  Email, "Confirm email" חייב להיות **פעיל**.

**שום דבר לא מתפרסם לפני שליחה.** פתיחת מסך "שליחה ללקוח" לא משנה כלום. דף הטיול נפתח לצפייה וקישור
ההצטרפות נוצר **רק** כשהסוכן לוחץ "שליחה בוואטסאפ" או "העתקת ההודעה".

## 9. מה לא קיים בבטא

| לא קיים | מה אומרים לסוכן במקום |
|---|---|
| סוכנות עם כמה סוכנים שרואים טיולים משותפים | כל סוכן חשבון נפרד. זה השלב הבא |
| מייל נכנס (להעביר אישור הזמנה למייל והטיול מתעדכן) | מעלים את הקבצים ב"טיול חדש מהמסמכים" |
| חיבור ל-CRM (Fireberry, monday) | אין. הטיול חי ב-TripCraft |
| WhatsApp API (שליחה אוטומטית) | הכפתור פותח וואטסאפ בטלפון של הסוכן עם הודעה מוכנה. הסוכן לוחץ "שלח" |
| חיוב ותשלום | הבטא חינם. המכסות מנוהלות ידנית אצלך |
| אופליין | אין. צריך אינטרנט |
| תבניות טיול | הוצאו מהבטא (החלטה #31) |

## 10. פרטיות

בדף `/privacy` יש סעיף "5. סוכני נסיעות". בקצרה:
- פרטי חשבון הסוכן (שם סוכנות, טלפון, מייל, מועדים) גלויים למנהלי TripCraft לצורך אישור והשעיה.
- נמדדים עלות ה-AI, מספר הקריאות ל-Google ומספר הטיולים — **בלי תוכן הבקשות**.
- שם הלקוח והטלפון גלויים רק לסוכן. **הסוכן אחראי לקבל את הסכמת הלקוח**, ו-TripCraft מעבדת אותם עבורו.
- מסמכים שהסוכן מעלה לבניית טיול נשלחים ל-Anthropic כדי לחלץ מהם פרטים, ונשמרים באחסון הפרטי בתיקייה שלו.
- וואטסאפ: הקישור נפתח במכשיר של הסוכן. TripCraft לא שולחת כלום לוואטסאפ.
- הלוגו באחסון ציבורי — מי שיש לו את כתובת הקובץ יכול לפתוח אותו. שם הסוכנות שמוצג הוא השם שאושר.
- בעל הטיול רואה כמה מהנוסעים העלו דרכון — לא את המסמך עצמו (סעיף 4).

**בבטא מדגימים רק על הסוכנות לדוגמה** — בלי נתוני לקוחות אמיתיים (ההחלטה שלך).

### הסוכנות לדוגמה (סקריפט הדמו)

`scripts/seed-demo-agency.mjs` הופך חשבון קיים אחד ל"טיולי הגשר — סוכנות לדוגמה" (טלפון בדוי 03-0000000)
עם 6 טיולים בדויים:

| טיול | סטטוס ברשימה |
|---|---|
| רומא עם הילדים (משפחת אלון, 4 נוסעים) | חסר משהו — חסר דרכון אחד |
| בר המצווה של יונתן בפראג (40 נוסעים, שומרי כשרות) | נשלח. ראשון עד חמישי, עלייה לתורה ביום שני — כלום בשבת |
| פריז, שבת ברובע היהודי (זוג שומר כשרות) | יוצא בקרוב (חמישי עד רביעי, היציאה תמיד בשבוע הקרוב). שבת בתוך הטיול: ביום שישי קניות בבוקר וארוחת שבת בלי שעה, עם זמן כניסת השבת ליד היום. בשבת אין פעילות ואין טיסות, והסיור ביום ראשון — אף פריט לא מסומן "בשבת" |
| קבוצת צעדים בברצלונה (12 נוסעים, מדריך) | בחו"ל |
| אמסטרדם על אופניים | טיוטה (לא נשלח) |
| לונדון לזוג | חזר |

- כל השמות בדויים, טלפון המדריך 050-0000xxx, המלונות "Esempio / Příklad / Exemple / Ejemplo / Example".
- **ללקוחות אין מספר טלפון**, כדי שלחיצה בטעות על "שליחה בוואטסאפ" לא תשלח הודעה לאדם אמיתי. בהדגמה
  מקלידים בשליחה את המספר שלכם.
- **אין קבצים.** "דרכונים" הם שורות מסמך בלי קובץ ("דמו, אין קובץ"), כדי שמונה הדרכונים יראה מצבים שונים.
- **אף נוסע לא "הצטרף".** הצטרפות דורשת חשבון אמיתי, והסקריפט לא יוצר חשבונות מזויפים. לכן ליד רוב
  הטיולים כתוב "אף נוסע עוד לא הצטרף", והם מופיעים ב"דורשים טיפול". בהדגמה מצטרפים בטלפון שני (ראו
  demo-script.md).
- התאריכים מחושבים מהיום, אז כל הרצה מחדש מעדכנת אותם. קישורי השיתוף וההצטרפות נשמרים.

הרצה:
```
# במחשב, מול Supabase המקומי:
npm run seed:demo-agency -- agent-v1@test.local
npm run seed:demo-agency -- agent-v1@test.local --remove     # מוחק רק את מה שהסקריפט יצר

# בייצור (רק כשתחליט): קודם מגדירים את כתובת הפרויקט ומפתח service_role מ-Supabase → Settings → API
$env:SUPABASE_URL="https://<project>.supabase.co"; $env:SUPABASE_SERVICE_ROLE_KEY="<המפתח>"
npm run seed:demo-agency -- <המייל של החשבון> --prod
# מיד אחרי: מוחקים את המפתח מהחלון, שלא יישאר פתוח
Remove-Item Env:SUPABASE_SERVICE_ROLE_KEY
```
בלי `--prod` הסקריפט מסרב לרוץ מול כתובת שאינה מקומית. עם `--prod` הוא מציג בדיוק מה יעשה ומבקש להקליד
שוב את המייל. הוא **מסרב** לחשבון סוכן מושעה (תמיד), ולחשבון שכבר יש עליו סוכנות אחרת או מיתוג אחר — אלא אם
מוסיפים `--force`, שמחליף אותם בסוכנות לדוגמה. `--remove` מוחק רק את 6 הטיולים האלה (לפי מזהים קבועים של החשבון), ומחזיר את החשבון למשתמש
רגיל רק אם עדיין רשום עליו שם הסוכנות לדוגמה. אל תריץ אותו על החשבון הראשי שלך אם תרצה בו מיתוג אחר.

## 12. מילון מונחים

| מונח | בעברית פשוטה |
|---|---|
| **RLS** (Row Level Security) | כללים בתוך מסד הנתונים שקובעים לכל שורה מי רשאי לראות או לשנות אותה. גם בקשה שעוקפת את המסך נבדקת |
| **migration** | קובץ SQL ממוספר (למשל 022) שמשנה את מבנה מסד הנתונים. מריצים כל אחד פעם אחת, לפי הסדר |
| **Edge Function** | קוד שרץ בשרת של Supabase ולא בטלפון. כך מפתח ה-AI לא מגיע לדפדפן. אצלנו: `generate` ו-`ask` |
| **bucket** | "תיקייה ראשית" לקבצים ב-Supabase. פרטי = נפתח רק בקישור זמני למורשה. ציבורי = כל מי שיש לו את הכתובת |
| **RPC** | פונקציה במסד הנתונים שהאפליקציה קוראת לה בשמה, למשל `agent_trip_board` (רשימת הטיולים של הסוכן) או `admin_decide_agent` (אישור / השעיה). הפונקציה בודקת בעצמה מי קורא לה |
| **service_role** | מפתח "מנהל-על" של Supabase שעוקף את RLS. רק לסקריפטים כמו סקריפט הדמו. לא משתפים ולא שמים באתר |
| **admin / agent** | תפקידים בטבלת `user_roles`. admin = אתה. agent = סוכן מאושר |
