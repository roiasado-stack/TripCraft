# Push notifications (web push), phase 1

Date: 2026-10-22 · Route: Blueprint · Status: **awaiting Roi's approval**
Background: the proposal of 2026-10-08 (memory `tripcraft-notifications-proposal`).

## Goal

A traveller who turns notifications on gets a push on the phone, even with the app closed:
- **A new trip update.** Every member of the trip gets it, except the person who wrote it.
- **A join request.** Only the trip owner gets it, when someone joins by link and is waiting for approval.

Clicking the notification opens the right screen (the trip's home tab, or the members screen).
Settings has a screen to turn it on, pick which kinds to get, and send a test notification. Inside
a trip you can mute that trip only.

Roi's decisions (2026-10-22): phase 1 = trip updates + join requests + settings · push only, no email.

## Non-goals

- No "flying tomorrow", Shabbat, "7 days before" or morning brief. Those are phase 2, after the
  fix for flight times that are 3 hours off.
- No email, WhatsApp or SMS. No marketing pushes, ever.
- No offline support. The service worker only receives pushes, has no `fetch` handler and caches nothing.
- Demo visitors (anonymous) don't get notifications and can't subscribe.
- No production deploy. Everything is built and tested locally and on TripCraft-dev only.

## Design

**Data (migration 026):**
- `push_subscriptions`: `user_id` (default `auth.uid()`), `endpoint` UNIQUE, `p256dh`, `auth`,
  `user_agent`, `created_at`, `last_ok_at`. RLS: a user sees, adds and deletes **only their own
  rows**. An anonymous user can't add a row (`is_anonymous` from the JWT). No `anon` grant.
- `notification_settings`: one row per user: `trip_updates bool`, `join_requests bool` (both default true).
  RLS: own row only.
- `trip_notification_mutes (user_id, trip_id)`: mute a single trip. RLS: own rows, and only for a
  trip they can see (`can_view_trip`).

**Sending:**
- An `AFTER INSERT` trigger on `trip_updates`, plus a trigger on `trip_members` when a row enters
  `pending`, calls the `notify` Edge Function through `pg_net`. The function URL and a shared secret
  sit in Supabase Vault, and the function rejects a call without the secret.
- `notify` (Deno, service role) decides who gets the push. For an update: the trip's owner and active
  members, minus the author, minus anyone who muted the trip or turned it off. For a join request:
  the owner only. It sends with VAPID keys (secrets `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT`)
  and deletes subscriptions that came back 404/410.
- Payload: the trip's name plus the update title, or "בקשת הצטרפות חדשה". Web push content is
  encrypted end to end, so Apple and Google can't read it.

**Client:**
- `public/sw.js`: `push` shows the notification, and `notificationclick` focuses or opens the URL.
  It is registered in `main.tsx`.
- `src/lib/push.ts`: subscribe and unsubscribe, plus a pure check of whether this device can get
  pushes (iOS without "add to home screen" → instructions instead of a button). Unit tests for the
  pure logic.
- Settings → "התראות" section: turn on for this device, two toggles, "שלח התראת ניסיון".
- Trip menu → "השתק את הטיול הזה".

**Privacy:** `/privacy` gets an update that names Apple/Google/Mozilla push services as a new third
party, says what is sent, and says how to turn it off.

## Phases

### Phase 1: DB + `notify` function
Touches: `supabase/migrations/026_web_push.sql`, `supabase/functions/notify/`, `supabase/tests/`.
Acceptance criteria:
1. `test:db`: user A doesn't see and can't delete user B's subscription. A demo user can't add one.
   `anon` has no grant on any of the three tables.
2. `test:db`: an update in a trip queues a send to the members only, not the author, not someone
   who muted the trip, and not a user who isn't in the trip.
3. `test:db`: a join request queues a send to the owner only. An ordinary trip with no members queues nothing.
4. `notify` without the secret returns 401. With the secret it sends a real push to a test
   subscription (on TripCraft-dev), and a 410 deletes the row.
5. The migration ends with the check query (RLS on every table, no anon grant) returning 0 rows.

### Phase 2: client + settings + privacy
Touches: `public/sw.js`, `src/main.tsx`, `src/lib/push.ts`(+test), `SettingsPage.tsx`, trip menu, `LegalPages.tsx`.
Acceptance criteria (verified on a phone-width screen + a real device against TripCraft-dev):
1. Settings → "התראות" → turn on → the browser asks for permission → a row appears in `push_subscriptions`.
2. "שלח התראת ניסיון" → a notification arrives on the device.
3. Participant B publishes an update → owner A gets a push. B doesn't get one. Click → the trip opens.
4. Someone joins by link with approval → the owner gets a push. Click → the members screen opens.
5. Mute the trip → no push from it. Toggle "עדכוני טיול" off → no update pushes, join requests still come.
6. iOS Safari not from the home screen → instructions show instead of a button. A demo visitor doesn't see the section.
7. `/privacy` names the push services. Everything is RTL, Hebrew and AA in light and dark mode.

## Production (later, only with Roi's approval)
Paste 026 in the SQL Editor, deploy `notify`, set 3 VAPID secrets + the Vault secret, then deploy

## Risks
- iOS: works only after "add to home screen" (16.4+). Most Israeli travellers are on iPhone, so the
  instructions screen matters.
- `pg_net` on the dev project needs to be enabled (an extension, no cost).
